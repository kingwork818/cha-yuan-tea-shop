2. Maintenance and responsibility

The merchant owns the source code, the hosting account and the database. There is no platform vendor, no app marketplace, and no third party with standing access to customer data. Security patches and dependency updates are applied by the merchant through the same versioned deployment process.

3. Payment integration

Card payments are integrated directly with the acquirer's own card gateway (local card, 3-D Secure 2) — not through a third-party checkout overlay or hosted storefront. For every transaction:

  1. The cardholder enters card details on the merchant's own checkout page over HTTPS.
  2. The application validates the input (check digit, expiry, CVV length) and relays it to the acquirer's gateway over TLS for authorisation.
  3. Where 3-D Secure 2 requires it, the cardholder completes the issuer's authentication challenge.
  4. The result is received by callback and reconciled against the order.

Card data is never stored. Neither the database nor the application logs contain a card number or CVV at any point; request bodies are redacted before logging. The order record retains only the card brand, the last four digits, the amount, the currency and the acquirer's payment and order identifiers — the minimum required to reconcile a transaction, answer a customer query and issue a refund.

Because the card is captured on a page served by the merchant's own application and relayed by it, this is a direct-post integration, and the merchant's PCI DSS self-assessment category is SAQ A-EP. The website copy is aligned with this and makes no SAQ A claim.

4. Security controls

  • HTTPS end to end; HTTP redirects to HTTPS; HSTS enabled
  • Content Security Policy, X-Content-Type-Options, X-Frame-Options, Referrer-Policy and Permissions-Policy set on every response
  • No card data in the database, logs or error reports
  • Back-office login rate-limited to 8 attempts per 5 minutes per IP; sessions signed, server-side revocable, expiring after 12 hours
  • Every back-office action — refund, status change, stock change, export, sign-in, failed sign-in — recorded in an append-only audit trail with the account and source IP
  • Automated test suite on every deployment: access control, payment callback pipeline, mail delivery, and accuracy of published policy copy
  • Health-checked deployment with automatic restart; database on a persistent disk separate from the application container
